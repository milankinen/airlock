# Rust 1.94 → 1.97

Follow-up to the dependency refresh: bump the toolchain three releases
so the one dependency held back on MSRV can move, and absorb the new
clippy lints that come with it.

## Where the version actually lives

Only two places pin a Rust version:

- `rust-toolchain.toml` — `channel = "1.97"`
- `app/airlockd/builder.dockerfile` — `FROM rust:1.97-slim-trixie`

Everything else derives from those. CI installs Rust via
`jdx/mise-action` + rustup, which reads `rust-toolchain.toml`, so the
workflow files needed no edit. `dev.dockerfile` calls a bare `rustup
install` against the bind-mounted workspace — same story. The virtiofsd
builder uses the floating `rust:1-slim-trixie` and tracks stable on its
own.

`CONFIG_RUSTC_VERSION` in the `app/vm-kernel/config-*` files looks like
a pin but isn't ours — `CONFIG_RUST` is not set, so the kernel builds
with no Rust involvement and the value is a leftover probe result.

## sysinfo 0.38 → 0.39

The only dependency the toolchain was blocking. `default_memory()` in
`app/airlock-cli/src/config.rs` is the sole call site and the surface it
touches (`System::new_with_specifics`, `RefreshKind::nothing()`,
`MemoryRefreshKind::everything()`, `total_memory()`) is unchanged.
Pulls in `objc2-open-directory` on the macOS side.

A full `cargo update` under the new toolchain moved nothing else —
resolver v3 is MSRV-aware, so it was worth checking whether 1.94 had
been silently holding patch releases back. It hadn't. `matchit` and
`generic-array` are still behind, both for the same upstream `=` pins as
before; neither is MSRV-related.

## New clippy lints

The workspace denies `clippy::pedantic`, so three lints that landed
between 1.94 and 1.97 turned into build failures.

**`map_unwrap_or` now covers `Result`, not just `Option`.** Six sites,
all mechanical — `.map(f).unwrap_or(d)` → `.map_or(d, f)`, or
`.is_ok_and(f)` where the default was `false`:

    app/airlock-cli/src/cli/cmd_secret.rs
    app/airlock-cli/src/oci.rs            (×2, both is_ok_and)
    app/airlock-cli/src/oci/layer.rs
    app/airlock-cli/src/settings.rs
    app/airlock-cli/src/vault.rs
    app/airlock-monitor/src/tabs/monitor/network/row.rs

**`duration_suboptimal_units`** wants the largest readable unit.
`Duration::from_secs(600)` → `from_mins(10)` in
`airlockd/src/init/linux/disk.rs`, and `from_secs(60)` → `from_mins(1)`
in `cli/cmd_start.rs`. `from_mins` is stable as of this toolchain, which
is presumably why the lint exists now.

**`manual_checked_ops`** flagged the guarded division in the monitor's
memory gauge. Rewritten as `checked_div(...).unwrap_or(0)`:

    (self.used_bytes * 100)
        .checked_div(self.total_bytes)
        .unwrap_or(0)
        .min(100) as u8

Same result for `total_bytes == 0` — the old branch returned 0
explicitly, `checked_div` returns `None` and the `unwrap_or` supplies
it.

All three are readability lints; no behaviour changed anywhere.

## Verification

`mise run test` (180 tests) and `mise run lint` both pass. The airlockd
musl cross-build — `cargo check --release -p airlockd --target
aarch64-unknown-linux-musl`, which is what the docker builder runs —
also passes.

Not exercised locally: the bundled `airlock-cli` binary won't link
without `target/vm/{Image,initramfs.gz,cloud-hypervisor,virtiofsd}` for
its `include_bytes!` slots, and those need docker to build. `Assets::init`
is `#[cfg(not(test))]`, which is why the test and lint paths don't need
them — but it means CI's stage-3 build jobs are the first real check of
the release binary on 1.97.
