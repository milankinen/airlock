# ACP proxy

Editors start an ACP agent in any directory. The project directory comes
only with the first session request that has a `cwd`. `airlock exec`
cannot work without the directory.

## Change

`airlock acp [OPTIONS] [<cmd> [args...]] [-- <args...>]` is a proxy
between the editor and the agent. Arguments after `--` follow the
command and its arguments, or give the command. Without a command the
exit code is 2. Options:

- `--pass-client-capabilities`
- `--follow-git-worktree`
- `-e/--env KEY=VALUE` (repeatable) and `-l/--login`, as in `airlock exec`
- `--log-level trace|debug|info|warn|error` (env `AIRLOCK_LOG_LEVEL`,
  default `info`)

The proxy answers `initialize` itself. It starts the agent at the first
session request with a `cwd`. That `cwd` selects the running sandbox.
The manual page is `tips/editor-acp.md`.

- No running sandbox: the editor gets a JSON-RPC error for the session.
- One agent for each proxy. A later session in another sandbox is
  refused.
- `cwd` must be absolute. The proxy maps it to the guest directory.
  `--sandbox-cwd` of the sandbox is honored. `airlock exec` now honors
  `--sandbox-cwd` too.
- On an auth error (-32000), the proxy adds a hint to log in inside the
  sandbox.
- Start and handshake timeout: 60 s in total. When the editor closes,
  the proxy waits 5 s for the agent, then kills it. When the editor
  closes during the agent start, the proxy stops the start and gives no
  reply.
- Signals: the proxy watches the host signals from the first agent
  start. Before the handshake completes, a signal kills the agent and
  the proxy exits with 128 + signal number. After the handshake, the
  agent gets the signal. While the proxy waits for the agent exit, a
  signal kills the agent at once.
- Log file `acp.log` in the data directory. A log file is cut to its
  last 1 MiB at open, and again when the process wrote more than 2 MiB
  to it (best effort; also `airlock.log`). One lock in the process keeps
  the writes and the cut in order. Many proxies append to it without a
  lock. Each line starts with `[pid]`. `info` logs initialize, session
  requests, agent start, handshake, failures, exit code, editor close
  and kill. `debug` adds other methods, refused or
  dropped messages and removed MCP servers (method and sandbox only, no
  `session/update`). `trace` logs every full message, so it logs prompts
  and file content. Each message line is `<from> -> <to>: <message>`,
  with `client`, `agent` or `airlock` as peers. The proxy logs a message
  once per hop: at the send for a forwarded or made message (after the
  filter changes it), and at the point where the proxy keeps it.

## Security

The agent is untrusted. The editor has host features that the agent must
not use.

- **Capability allowlist.** The proxy sends the agent only
  `elicitation.form`, `session` and `auth` without `terminal`. It drops
  `fs`, `terminal`, `_meta`, URL elicitation and unknown keys. It forces
  protocol version 1.
- **Agent message allowlist.** Only `session/request_permission` and
  form `elicitation/create` requests go to the editor. Other requests
  get an error reply. Notifications: only `session/update`,
  `elicitation/complete` and `$/cancel_request`.
- **Re-serialized lines.** The proxy parses each agent line and sends a
  single JSON object again. Batches and non-JSON lines are dropped.
- **No MCP over ACP.** The proxy removes `type = "acp"` entries from
  `mcpServers`, because those tools run in the editor.
- **Agent features.** The proxy tells the editor the features before the
  agent runs. It then refuses editor requests for features that the
  agent lacks: session load, HTTP and SSE MCP servers, and image, audio
  and embedded prompt content.
- **Memory limit.** One agent output line can have at most 16 MiB. A
  longer line, also a line without end, kills the agent in both modes.
  Before the handshake, the session request then gets an error. After
  it, the proxy exits with the exit code of the agent. An agent that
  does not read its input (1024 lines wait) is killed too. The client
  output and the agent output have small queues, so a slow editor
  slows the agent and the output waits in the sandbox. The agent stderr
  does not wait: when the host stderr queue is full, the proxy drops
  the stderr data and logs the dropped byte count. At exit, the proxy
  waits for the stderr write for the shutdown grace time only.
- **Message kinds.** Only a message with an `id` and no `method` key is
  a response. A message with a `method` that is not a string is dropped.
- **Agent argv.** `info` logs only the agent command name. The full
  argv can hold secrets and only `trace` logs it.
- **`cwd` comes from the editor.** The sandbox lookup refuses symlinks.
  A later session must use the same sandbox.
- `--pass-client-capabilities` turns the filters off. The agent can
  then act on the host. The manual warns about this.

## Not supported

- Login from the editor UI (the proxy sends no login methods).
- Several sandboxes in one proxy.
